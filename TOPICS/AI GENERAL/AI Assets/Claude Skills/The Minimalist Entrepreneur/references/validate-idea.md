# Validate Idea

## Purpose

Validate whether a business idea is worth pursuing using a demand-first, manual-first approach.

---

## When to Apply

- Already have a business idea
- Unsure if idea is viable
- Before building product or writing code
- Need evidence of real demand

---

## Core Principle

Validation is done through **selling, not building**.

A valid idea must demonstrate:
- real demand
- willingness to pay
- feasibility via manual execution

---

## Workflow

### Step 1 — Define the Problem

Clarify:

- Who exactly has this problem? (specific segment)
- How are they solving it today? (existing workaround = real competition)
- How painful is it? (minor inconvenience vs critical pain)
- Would they pay to remove this problem?

---

### Step 2 — Test Manual Solution

Before building anything:

- Solve the problem manually
- Document each step of the process
- Deliver value directly to users without automation

Goal:
- Prove the solution works in reality
- Understand the actual workflow

---

### Step 3 — Validate Payment

Test willingness to pay:

- Talk to at least 10 potential users
- Confirm at least 3 willing to pay (or actual payment)
- Identify a natural price point

No payment signal → not validated

---

### Step 4 — Pre-Build Check

Evaluate:

- Can a first version be delivered within 2–3 days?
- Does it create measurable improvement for users?
- Are users willing to pay now (not later)?
- Can feedback be collected quickly?

---

## Red Flags

- No existing workaround or current solution
- Cannot identify 10 real users with this problem
- Validation based only on opinions (friends, assumptions)
- Requires educating users about the problem
- Targeting a community you do not belong to

---

## Green Flags

- Users already pay for inferior alternatives
- Manual solution has been tested successfully
- Community frequently complains about the problem
- Problem and customer can be described clearly
- Personal experience with the problem (own pain)

---

## Output

Provide a clear decision:

- **Validated**  
  Strong demand and payment signal → proceed to MVP

- **Needs more validation**  
  Insufficient evidence → define next validation actions

- **Pivot**  
  Weak or incorrect assumptions → redefine problem or target
